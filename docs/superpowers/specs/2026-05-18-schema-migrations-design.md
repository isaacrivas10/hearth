## Purpose

Land the schema-evolution system that turns plugin entity declarations into safe, auditable DB changes. The kernel's job is **orchestration and safety**:

- Discover plugins and their declared entities.
- Apply per-plugin schema changes in topological order.
- Classify each op as safe or destructive, and refuse to apply destructive ops without an explicit human confirmation.
- Hold a single-writer lock so concurrent applies cannot interleave.
- Audit every applied revision (who, when, what was acknowledged).

**Alembic does the actual schema work.** Diff generation (`alembic.autogenerate`), DDL execution (`alembic.op.*` with SQLite batch mode), branch head tracking (one row per branch in the shared `alembic_version` table), revision file discovery, dependency graph — all Alembic. Hearth does not re-implement any of this.

The system has three triggers and one mechanism:

| Trigger | Caller | Outcome |
|---|---|---|
| **Pre-flight** (CI) | `hearth migrate check` in plugin CI | Pass/fail: are revision files up-to-date with entity declarations? |
| **Apply** (deploy) | `hearth db migrate` on the production host | Per-plugin walk; safe revisions apply, destructive ops confronted via interactive surface |
| **Boot** (runtime) | Kernel during application startup | Refuse to start if pending, or auto-apply per `HEARTH_DB_MIGRATE` policy |

## Scope

In: per-plugin Alembic environments built dynamically from the registry; autogenerated revision files in standard Alembic format with one Hearth addition (a `branch_labels = ("<plugin>",)` line) plus a machine-readable `HEARTH_UPGRADE_OPS` classification artifact; optional `data_upgrade(uow)` / `data_downgrade(uow)` Python hooks for seed data and entity-typed backfills; destructive-op classifier over Alembic's `MigrateOperation` types; `apply(plan, confirm=...)` extension point for multiple confirmation surfaces; CLI verbs (`hearth migrate generate|check`; `hearth db status|plan|migrate`); startup policies (`strict`, `safe`, `off`); rollback-aware artifacts (`downgrade()` mandatory at generation, audit log of what was applied); orphan-on-removal; per-plugin atomic apply; single-writer advisory lock.

Out v1: rollback execution (artifacts ready, command not shipped); online / zero-downtime migration; declarative destructive pre-authorization; marketplace install UX; plugin re-adoption tooling for orphaned tables; `@destructive("reason")` marker on `data_upgrade` (data hooks are always classified safe v1).

## Why this shape

The decisions captured below are the conclusion of an earlier brainstorming session (paused after Registry + CLI was identified as a prerequisite) and the 2026-05-18 amendments. They are not relitigated here.

1. **Use Alembic as a tool, not a kernel dependency to be hidden.** SQLAlchemy is hidden because it is the kernel's persistence machinery — changing it would break plugins. Alembic is a tool that operates *on* the schema; it is not kernel internals. Plugin authors writing `from alembic import op; import sqlalchemy as sa` in migration files is normal and welcome. (See "Walled garden clarification" below.)
2. **Plugins ship standard Alembic revision files**, autogenerated by `hearth migrate generate` and reviewed/committed by the author. One Hearth-specific addition: `branch_labels = ("<plugin>",)` ties each revision to its owning plugin.
3. **Generate-and-vet at build, apply at runtime.** Same code path, three triggers (pre-flight, apply, boot).
4. **Per-op interactive acknowledgment for destructive ops.** The kernel exposes a `confirm(revision, op) -> bool` callback. CLI implements it as a TTY prompt; future surfaces (HTTP installer, web UI, WhatsApp bot) implement it for their channel.
5. **Plugin removal orphans tables by default.** Audit log identifies which tables belonged to a now-uninstalled plugin so v2 can ship re-adoption.
6. **Forward-only apply v1; artifacts are rollback-ready.** Every revision ships `upgrade()` and `downgrade()` from day one (Alembic standard). The audit log records who acknowledged what, when. V2 ships rollback by calling `alembic downgrade` per plugin in reverse topological order.

## Walled garden clarification

ADR-0006 says plugins never import from `sqlalchemy`. That rule is about **kernel persistence internals** — the ORM the kernel uses to make plugin code persistent without that code knowing how. Hiding it means the kernel can change persistence (cache layer, sharding, even swap ORMs) without plugin churn.

Alembic is different. It is a *tool* that operates on the database schema, not part of the kernel's runtime contract. Plugin authors writing Alembic revisions are doing the same thing operators do in any SQLAlchemy-backed project: writing schema-migration code in the standard format the community uses. Hiding Alembic would mean reinventing its op vocabulary, its diff engine, and its revision file format — for no isolation benefit (a revision file runs once, then is done; it has no runtime coupling to anything).

**The rule, clarified:** plugins never import from `sqlalchemy` *in runtime code* (entities, actions, events, jobs, views). Migration files in a plugin's `migrations/` directory are tooling and may freely import from `alembic` and `sqlalchemy`. This clarification will be appended as an amendment to ADR-0006 when the implementation lands.

**Enforcement is by convention and code review, not technical isolation.** Migration files run in the kernel's process and could technically import anything (`hearth.kernel.transaction`, the engine, the registry). The project treats this the same as trusting third-party plugin code — violations are caught in review, not at runtime. The boundary is meaningful but not sandboxed.

## Design

### Module layout

```
hearth/
  kernel/
    migrations/
      __init__.py          # Public-to-CLI internals
      alembic_config.py    # Build Alembic Config dynamically from the registry
      planner.py           # Walk per-plugin revisions, produce ordered apply list
      classifier.py        # classify(op: MigrateOperation) -> "safe" | "destructive"
      applier.py           # Advisory lock + per-plugin apply loop + confirm callback
      audit_log.py         # _hearth_schema_log ORM + read/write helpers
```

Notably small — the diff engine, DDL execution, revision discovery, per-branch head tracking are all imported from Alembic and used directly.

The plugin-author surface is **`alembic`** (standard) plus `hearth.migrations` for the `OpSummary` dataclass used in the per-revision classification artifact (see "Revision file format" below). That's the entire kernel-facing import a revision file needs.

### The lifecycle-event model

A "migration event" is a transition: current applied state → target state. The kernel:

1. Walks the registry, getting `(plugin, package_path, head_revision_in_package)` for each installed plugin.
2. Builds an Alembic `Config` in-memory with `version_locations` = list of plugin migrations dirs, `target_metadata` = merged MetaData (so cross-plugin FKs resolve), and `render_as_batch = True` when the dialect is SQLite (required for any `ALTER TABLE` to work; the kernel detects the dialect from the engine URL). On SQLite, `migrate generate` emits `op.batch_alter_table(...)` wrappers for column-altering ops.
3. For each plugin in registry topological order:
   - Looks up the plugin's branch head in the shared `alembic_version` table (Alembic stores one row per active branch head) and compares against the latest revision in the plugin's package.
   - For each pending revision (Alembic's `ScriptDirectory.walk_revisions(current, head)`):
     - Imports the revision module and reads `HEARTH_UPGRADE_OPS` (the classifier verdict written at generate time; see the next section). If the list is missing, refuse the apply with a clear error.
     - For each entry where `destructive=True`, invokes `confirm(revision, op_summary) -> bool`. On `False`, abort the plan at that op.
     - On all-confirmed (or all-safe), calls Alembic to apply that single revision (`alembic.command.upgrade(config, revision_id)`).
     - Writes one audit row to `_hearth_schema_log`.
4. Moves to the next plugin.

The same flow runs in three contexts:

- **`hearth migrate check`** (CI): runs steps 1–2 plus, for each plugin, compares its declared `target_metadata` (current entity declarations) to its replayed-revisions metadata. Reports drift; exits nonzero if any. No DB connection needed. Used as a PR gate.
- **`hearth db migrate`** (operator): full flow. `confirm` is a TTY prompt.
- **Boot** (kernel startup): full flow up to apply, then policy decides (see "Startup behavior").

### Two audiences, two surfaces

| Audience | Sees | Never sees |
|---|---|---|
| **Plugin developer** | `hearth migrate generate <plugin>` (autogenerate a revision); `hearth migrate check <plugin>` (CI gate). They edit the generated file using standard Alembic idioms. | The kernel's classifier internals, the apply loop, the registry mechanics, the audit log. |
| **Operator** | `hearth db status` / `hearth db plan` / `hearth db migrate`. On `migrate`, either silence-then-success (all safe), or per-op confirmation prompts for destructive. | Revision files, Alembic itself, the diff engine. They know "install" and "the system told me this would delete data, do I want that?" |

A **third future audience** — a transport plugin embedding the installer in its own UX (e.g., a web admin UI confirming destructive ops over HTTP) — is supported by the same `Applier.apply(plan, confirm=...)` API the CLI uses. V1 ships the CLI surface only; the API is the extension point.

### Revision file format (standard Alembic + classification artifact)

```python
# plugins/auth/hearth_auth/migrations/0003_add_user_phone.py
"""Add phone column to User."""

from alembic import op
import sqlalchemy as sa

from hearth.migrations import OpSummary

revision = "0003"
down_revision = "0002"
branch_labels = ("auth",)
depends_on = None


# Machine-readable summary of upgrade()/downgrade() with the classifier's verdict.
# Generated by `hearth migrate generate`; validated against the live upgrade()
# body by `hearth migrate check`. The kernel reads these at apply time to drive
# destructive-op confirmation prompts. Regenerate via
# `hearth migrate generate --refresh` if you hand-edit the upgrade() body.
HEARTH_UPGRADE_OPS: list[OpSummary] = [
    OpSummary(kind="AddColumn", desc="ADD COLUMN user.phone (nullable)", destructive=False),
]
HEARTH_DOWNGRADE_OPS: list[OpSummary] = [
    OpSummary(kind="DropColumn", desc="DROP COLUMN user.phone", destructive=True),
]


def upgrade() -> None:
    op.add_column("user", sa.Column("phone", sa.String, nullable=True))


def downgrade() -> None:
    op.drop_column("user", "phone")
```

**What's standard Alembic:** `revision`, `down_revision`, `branch_labels`, `depends_on`, `upgrade()`, `downgrade()`, the `op` and `sa` imports. Anyone with Alembic experience can read and write these unchanged.

**What's Hearth-specific:**

- `branch_labels` convention: a single-element tuple naming the owning plugin.
- `HEARTH_UPGRADE_OPS` and `HEARTH_DOWNGRADE_OPS`: module-level lists of `OpSummary` records — the classifier's verdict, computed at generate time, stored in the file so the kernel can read it at apply time without trying to introspect Alembic's opaque `upgrade()` body. `OpSummary` is a frozen dataclass exported from `hearth.migrations`:

  ```python
  @dataclass(frozen=True)
  class OpSummary:
      kind: str             # Alembic op class name, e.g. "AddColumn"
      desc: str             # Human description for prompts and audit log
      destructive: bool     # The classifier's verdict
  ```

**Why store the classification in the file** rather than re-derive it at apply time: a written `upgrade()` is opaque Python (it calls `op.*` against Alembic's runtime context — there is no public API to recover the list of operations from a `Script` after it's been written). The viable options are (a) classify at generate, store the verdict; (b) re-run autogenerate diffing at apply time; (c) intercept `op.*` calls with a recording shim. (a) is the most pragmatic — the classifier already runs at generate time to emit `# DESTRUCTIVE:` comments for the author's review; writing the same data as machine-readable lists is a marginal addition.

**Drift detection.** `hearth migrate check` re-runs autogenerate in-memory and compares the would-be `HEARTH_UPGRADE_OPS` against what's in the file. Hand-editing `upgrade()` without refreshing the lists fails `check` with: "operations drift detected: file claims X but upgrade() body would produce Y — run `hearth migrate generate --refresh`."

`check` also enforces a 1:1 correspondence between the presence of data hooks and their `OpSummary` entries: if `data_upgrade` is defined, exactly one `OpSummary(kind="DataMigration", ...)` must appear in `HEARTH_UPGRADE_OPS`; same for `data_downgrade` / `HEARTH_DOWNGRADE_OPS`. A mismatch fails CI: "revision defines `data_upgrade` but `HEARTH_UPGRADE_OPS` has no `DataMigration` entry — operators reading `hearth db plan` would not see this side effect." Without this enforcement, an author can silently add data work that the operator never sees in the plan they approve.

**Missing classification lists.** If a revision file lacks `HEARTH_UPGRADE_OPS` (hand-authored, or pre-classifier), the kernel refuses to apply it: "revision lacks classification artifact; cannot determine destructive ops. Run `hearth migrate generate --refresh` or add the lists by hand." No silent fallback — safety requires knowing the verdict.

**File location:** `plugins/<name>/hearth_<name>/migrations/NNNN_<slug>.py`. Discovered by pointing Alembic's `version_locations` at the directory.

**Revision id:** `NNNN_<slug>` — 4-digit zero-padded per-plugin monotonic + slug. `depends_on` (Alembic field for *cross-branch* dependencies — different from the per-plugin chain) is normally `None`; if a plugin's revision genuinely requires another plugin's revision to land first, it goes here.

**Parallel-branch conflicts:** if two developers each add `0007_*.py` in parallel branches, git surfaces it as a file conflict. Resolution: rename one to the next available number and update its `down_revision`. The kernel does not auto-merge revision histories.

### Data migrations and seeding

Revisions can carry data changes alongside (or instead of) DDL. Two complementary mechanisms cover the cases:

**(1) Raw SQL via `op.execute(...)`** — Alembic's standard mechanism. Right for mass UPDATEs and other set-based work the database does best:

```python
def upgrade() -> None:
    op.add_column("user", sa.Column("first_name", sa.String, nullable=True))
    op.add_column("user", sa.Column("last_name", sa.String, nullable=True))
    op.execute(
        "UPDATE \"user\" SET "
        "  first_name = split_part(full_name, ' ', 1), "
        "  last_name  = NULLIF(split_part(full_name, ' ', 2), '')"
    )
    op.drop_column("user", "full_name")
```

**(2) Python `data_upgrade(uow)` / `data_downgrade(uow)`** — optional async functions at module scope. The kernel calls them in a `UnitOfWork` scoped to `PluginActor("<plugin>")` AFTER the DDL transaction commits. Right for seeding default rows, creating composite-Value-typed entities, anything that benefits from passing through the entity layer's validation:

```python
"""Seed default permissions."""

from alembic import op
import sqlalchemy as sa
from hearth.migrations import OpSummary

revision = "0002"
down_revision = "0001"
branch_labels = ("auth",)
depends_on = None


HEARTH_UPGRADE_OPS: list[OpSummary] = [
    OpSummary(kind="DataMigration", desc="Seed default permissions", destructive=False),
]
HEARTH_DOWNGRADE_OPS: list[OpSummary] = [
    OpSummary(kind="DataMigration", desc="Remove seeded permissions", destructive=False),
]


def upgrade() -> None:
    pass    # data-only revision; no DDL


def downgrade() -> None:
    pass


async def data_upgrade(uow) -> None:
    """Runs AFTER upgrade() commits, in a fresh UoW with PluginActor('auth').
    Idempotency is the author's responsibility — find-then-save patterns survive
    re-runs after a partial failure."""
    from hearth_auth import Permission, PermissionName

    defaults = [("orders", "read"), ("orders", "write"), ("users", "read")]
    for resource, action in defaults:
        name = PermissionName(resource=resource, action=action)
        if await uow.find_one(Permission, name=name) is None:
            await uow.save(Permission(name=name))


async def data_downgrade(uow) -> None:
    """Optional. Absent means no-op (default behavior when downgrade() drops
    the underlying table; data is removed with it). Provide this when the
    downgrade reverses a data change without dropping the table."""
    from hearth_auth import Permission, PermissionName
    for resource, action in [("orders", "read"), ("orders", "write"), ("users", "read")]:
        existing = await uow.find_one(Permission, name=PermissionName(resource=resource, action=action))
        if existing is not None:
            await uow.delete(existing)
```

**The contract:**

- **Discovery.** The kernel checks each revision module for `data_upgrade` / `data_downgrade` attributes. If absent, the data phase is skipped silently. Pure-DDL revisions look exactly as they always did.
- **Execution context.** A fresh `UnitOfWork` opened on the same engine, with `actor = PluginActor("<plugin>")`. The actor attribution matters for the audit trail: rows the migration creates should be attributed to the plugin, not to whichever operator happened to run `hearth db migrate` that day. The audit log answers "who created this permission row, when, and as part of which revision?" through three columns together — `applied_by` records the plugin actor, `applied_at` records the timestamp, and `revision_id` records the specific revision — rather than encoding all of that in a single string.
- **Idempotency.** Author's responsibility. `find_one` + conditional `save` is the standard pattern. If `data_upgrade` raises after `upgrade()` has committed, Alembic's branch head is already advanced — re-running `hearth db migrate` will skip `upgrade()` and jump straight back to `data_upgrade`. The function must be safe to re-execute.
- **Classification.** `DataMigration` is always classified `safe`. The classifier cannot statically analyze a Python function body. Destructive data work (mass-delete of historical rows) belongs in `upgrade()` as `op.execute(...)` so the SQL classifier sees it; or wait for a future `@destructive("reason")` marker if the slice exposes the need.
- **Event emission is disabled.** The data UoW is initialized with the outbox emitter suppressed. `uow.save(...)` and `uow.delete(...)` inside `data_upgrade` persist rows and audit-log entries normally but enqueue no outbox events. Migrations are not user-visible activity; subscribers should not react to seed data as if a real user had created it. A future plugin that genuinely needs event-on-seed can revisit this when the case is concrete.
- **Plan rendering.** Each revision with a `data_upgrade` adds one `OpSummary(kind="DataMigration", desc=..., destructive=False)` entry to `HEARTH_UPGRADE_OPS`. `hearth db plan` shows it in the per-revision listing so the operator sees "Revision 0002: seed default permissions" before applying.

**The known sharp edge — DDL committed, data failed.** Because Alembic owns the upgrade transaction, DDL commits before `data_upgrade` runs. If `data_upgrade` raises, the branch head has advanced but the data side is incomplete. We accept this for v1 in exchange for keeping Alembic's apply machinery intact. The mitigation is the idempotency contract: a re-run picks up where the failure left off, provided the author wrote `data_upgrade` to be idempotent.

**Seed-data workflow.** This is exactly the pattern for plugins shipping defaults that should appear on first install *and* on upgrade to a version that adds new defaults:

- `hearth-auth v1.0` ships revision `0001`: creates `permission` table, no defaults.
- `hearth-auth v1.1` ships revision `0002`: data-only revision seeding three default permissions.
- An operator on v1.0 upgrades to v1.1 and runs `hearth db migrate` — revision `0002` runs, the new permissions appear, the audit log records `applied_by = system` (or whichever operator triggered) and `destructive_ops_acked = []`.

The schema and the seed data are versioned together through the same channel. There is no separate "seeding step" to forget.

**Apps are plugins too.** "Plugin" here means "any Python package registered via `[project.entry-points."hearth.plugins"]`" — it includes the operator's own application code, not just third-party libraries. An operator's app that wants reproducible deployment data (default roles + permissions for their business, lookup tables, default categories) registers itself as a plugin, declares its dependencies, and ships migrations the kernel discovers and applies in topological order alongside everything else. A revision in the operator's app can import from its dependency plugins (`from hearth_auth import Role, Permission`) and seed their data via `data_upgrade(uow)` — the dependency plugins' tables already exist by then because the dependency graph guarantees apply order.

```python
# acme_storefront/migrations/0001_seed_roles.py
"""Seed acme-specific roles + permissions on top of hearth-auth."""

revision = "0001"
down_revision = None
branch_labels = ("acme_storefront",)

HEARTH_UPGRADE_OPS = [
    OpSummary(kind="DataMigration", desc="Seed acme roles + permissions", destructive=False),
]


def upgrade(): pass
def downgrade(): pass


async def data_upgrade(uow):
    from hearth_auth import Role, Permission, PermissionName

    permissions = [("orders", "*"), ("users", "read"), ("products", "*")]
    perm_rows = []
    for resource, action in permissions:
        name = PermissionName(resource=resource, action=action)
        existing = await uow.find_one(Permission, name=name)
        perm_rows.append(existing or await uow.save(Permission(name=name)))

    for role_name in ("Manager", "Cashier", "Owner"):
        if await uow.find_one(Role, name=role_name) is None:
            await uow.save(Role(name=role_name, permissions=perm_rows))
```

The kernel applies this revision after `hearth_auth`'s own migrations (dependency order). Adding more roles later is a new revision (`0002`, `0003`, …) — reproducible across deploys, audited, applied automatically.

**Migrations vs. actions, restated.** Data that is *part of your deployment's definition* (roles your app needs to function, lookup tables, default categories) belongs in migrations — reproducible, versioned, applied automatically on every fresh deploy. Data that your deployment's *users create at runtime* (the customer's first order, a manager changing a password) goes through actions. The boundary is "ships with my deployment" vs. "happens during my deployment's life."

### The audit log

Alembic owns the *source of truth* for what's applied: a single shared `alembic_version` table holds one row per active branch head, identifying which revision is currently applied for each plugin's branch. Hearth's table is a pure **audit overlay**:

```sql
CREATE TABLE _hearth_schema_log (
    plugin                   TEXT NOT NULL,
    revision_id              TEXT NOT NULL,
    description              TEXT NOT NULL,            -- human-readable revision summary (Alembic's docstring)
    applied_at               TIMESTAMP WITH TIME ZONE NOT NULL,
    applied_by               TEXT NOT NULL,            -- "kind:id" of the Actor
    destructive_ops_acked    JSON NOT NULL,            -- list of op descriptions explicitly confirmed; [] if none
    PRIMARY KEY (plugin, revision_id)
);
```

`description` mirrors the revision's docstring (Alembic's `Script.doc`) so an auditor reading the log can recognize the change without cross-referencing the revision file (which may have been edited or moved since application). `destructive_ops_acked` is a list of human-readable strings (`"DROP COLUMN user.email_legacy"`) for each destructive op the operator explicitly approved. Empty list means the revision was all-safe. This is what an auditor reads to answer "who authorized dropping that column?"

Created by `hearth db init` (along with the kernel's outbox table; Alembic's shared `alembic_version` table is created lazily on first apply).

**Existing installs created under the auth spec's `db init`:** the prior `db init` (pre-migrations convenience, per the auth spec amendment) created plugin tables alongside the kernel tables but did not populate any `alembic_version` rows. When `db migrate` runs for the first time against such an install, the planner sees existing plugin tables in the DB, no Alembic version rows for them, but revision files matching them. The planner treats this as "adopt without re-applying": for each plugin whose declared schema **structurally** matches the live DB schema (table existence, column existence + type family + nullability, primary keys, foreign keys — ignoring cosmetic differences like server-default text representation, type aliases, constraint naming), use Alembic's `stamp` command to mark the plugin's branch head as applied and write a `_hearth_schema_log` row with `applied_by = system:adopt`. If structural drift exists, refuse to start and surface the diff for operator resolution.

  **Known constraint:** `compare_metadata` returns cosmetic-only diffs frequently (server defaults rendered differently, `VARCHAR` vs `String`, index naming, constraint ordering). Adoption uses a narrower structural-only comparison, but the boundary between "structural" and "cosmetic" needs slice friction to pin down. Operators may still need to manually reconcile in edge cases.

**Orphan handling:** if a plugin is uninstalled, its `alembic_version` row and its rows in `_hearth_schema_log` stay. `hearth db status` reports them under "orphaned plugins." V2 will ship a re-adoption command; v1 leaves orphans alone (destructive table cleanup requires operator action through a tool that doesn't exist yet, by design).

### The diff and the plan

`hearth migrate generate <plugin>`:

1. Build the Alembic Config in-memory: `version_locations = [<this plugin's migrations dir>]`, `target_metadata` = full registry MetaData filtered via `include_object` callback to this plugin's tables (cross-plugin FKs still resolve because the merged MetaData is available for lookup).
2. Run `alembic revision --autogenerate --branch-label <plugin>` programmatically (`alembic.command.revision(..., autogenerate=True, branch_label=plugin)`).
3. Post-process the generated file: walk the autogenerated `MigrationScript.upgrade_ops` (the `UpgradeOps` structure is available *during* generation, just not after the file is written), classify each, and write the `HEARTH_UPGRADE_OPS` / `HEARTH_DOWNGRADE_OPS` lists. Also insert `# DESTRUCTIVE:` comments inline near risky `op.*` calls in the upgrade/downgrade bodies so the author sees the classifier verdict during code review.
4. Emit a commented stub for the optional Python data hooks at the end of the file:

   ```python
   # Optional: define data_upgrade / data_downgrade to seed or migrate data
   # using the kernel's UnitOfWork. The kernel runs them in a UoW scoped to
   # PluginActor("<plugin>"). Event emission is disabled for the data UoW.
   #
   # IMPORTANT — upgrade() commits BEFORE data_upgrade runs. If data_upgrade
   # raises, Alembic's branch head is already advanced; a re-run will call
   # data_upgrade again (via the recovery check) without re-running upgrade().
   # Write your function to be safe on repeated calls — find-then-save, not
   # unconditional insert.
   #
   # IMPORTANT — if you add data_upgrade, also append an OpSummary(kind=
   # "DataMigration", desc=..., destructive=False) entry to HEARTH_UPGRADE_OPS
   # above. `hearth migrate check` will fail otherwise: operators reading
   # `hearth db plan` need to see this side effect before approving the plan.
   #
   # async def data_upgrade(uow) -> None:
   #     ...
   #
   # async def data_downgrade(uow) -> None:
   #     ...
   ```

   Authors who don't need data hooks ignore the comment; those who do uncomment and fill in.
5. Print the file path. Author reviews, edits descriptions / refines autogenerated decisions / fills in data hooks if needed, commits.

   **Editable-install requirement:** writes go into the package's source tree (resolved via `importlib.resources.files(plugin_module)`). For a normal install this would land in `site-packages/`. The kernel detects editable status (PEP 660 `direct_url.json`, or `.dist-info/RECORD` outside `site-packages`); if not editable, aborts: "plugin `<name>` is not an editable install; revision generation must run from the plugin source tree (`pip install -e plugins/<name>`)."

`hearth migrate check <plugin>` runs steps 1–2 with autogenerate but writes nothing. If the diff is non-empty, fails: "drift detected, please run `hearth migrate generate`." Used as a PR gate.

### Destructive op classifier (v1 taxonomy)

`classify(op: MigrateOperation) -> Literal["safe", "destructive"]` runs at generate time (where Alembic's op instances are available with their fields). It inspects Alembic's own op types and the relevant fields shown below:

| Alembic op | Field(s) inspected | Classification | Notes |
|---|---|---|---|
| `CreateTableOp` | — | safe | |
| `DropTableOp` | — | **destructive** | |
| `AddColumnOp` | `column.nullable=True` | safe | |
| `AddColumnOp` | `column.nullable=False` + `column.server_default is not None` | safe | |
| `AddColumnOp` | `column.nullable=False` + `column.server_default is None` | **destructive** | Cannot succeed on non-empty table. |
| `DropColumnOp` | — | **destructive** | |
| `AlterColumnOp` | `new_column_name is not None` | safe | Rename. |
| `RenameTableOp` | — | safe | |
| `AlterColumnOp` | `modify_type` set; coercion lossless (int→bigint, varchar(50)→varchar(200)) | safe | |
| `AlterColumnOp` | `modify_type` set; coercion lossy (text→int, bigint→int, varchar(200)→varchar(50)) | **destructive** | |
| `AlterColumnOp` | `modify_nullable=True` (False → True) | safe | |
| `AlterColumnOp` | `modify_nullable=False` (True → False) | **destructive** | Existing NULLs would fail. |
| `CreateIndexOp` | — | safe | |
| `DropIndexOp` | `unique=True` | **destructive** | |
| `DropIndexOp` | `unique=False` | safe | |
| `CreateUniqueConstraintOp` / `CreateCheckConstraintOp` | — | **destructive** | Existing data could violate. |
| `CreateForeignKeyOp` | target column stable | safe | |
| `DropConstraintOp` | — | **destructive** | |
| `ExecuteSQLOp` (raw `op.execute(...)`) | — | **destructive** | Cannot statically analyze SQL; conservative. |
| `DataMigration` (presence of `data_upgrade` / `data_downgrade`) | — | safe | Author wrote it through the entity API. Destructive data work belongs in `op.execute(...)` so the SQL classifier sees it. |

Borderline cases are classified destructive. The classifier errs toward asking — the operator can always say yes; we cannot un-drop a column they didn't realize was being dropped.

### The `MigrationPlan` API

The kernel walks Alembic's revision graph to produce an ordered apply list. Ops are carried as `OpSummary` records read from each revision file's `HEARTH_UPGRADE_OPS`, not as live Alembic `MigrateOperation` instances (which exist only during autogenerate):

```python
@dataclass(frozen=True)
class PlannedRevision:
    plugin: str
    revision_id: str
    description: str
    ops: list[OpSummary]                    # read from HEARTH_UPGRADE_OPS
    destructive_ops: list[OpSummary]        # subset where .destructive is True


@dataclass(frozen=True)
class MigrationPlan:
    revisions: list[PlannedRevision]        # topological by plugin, then by revision_id

    @property
    def has_destructive(self) -> bool: ...

    def format(self, *, color: bool = False) -> str:
        """Human-readable rendering for the operator."""


async def apply(
    plan: MigrationPlan,
    *,
    config: alembic.config.Config,
    actor: Actor,
    confirm: Callable[[PlannedRevision, OpSummary], Awaitable[bool]] | None = None,
) -> AppliedReport:
    """
    Apply plan. For each destructive op, calls `confirm(revision, op_summary)`;
    if it returns False, apply halts at that op. Everything before commits;
    that op and everything after is not applied.

    If `confirm is None`, any destructive op aborts immediately.
    """
```

`apply` is the extension point. The CLI implements `confirm` as a TTY prompt; a future web installer implements it as an HTTP round-trip; tests implement it as `lambda *_: True`.

### The apply loop

**Single-writer invariant.** Before touching anything, the applier acquires an advisory lock on the target database for the duration of the entire plan. On PostgreSQL: `pg_try_advisory_lock(<hearth-magic>)`. On SQLite: `BEGIN EXCLUSIVE` against the audit log table held until plan completion. Lock acquisition has a short timeout (default 5s, configurable via `HEARTH_DB_MIGRATE_LOCK_TIMEOUT`); on contention, the applier aborts with "another migration is in progress; retry once it completes." This prevents two operators from running `hearth db migrate` concurrently, and prevents a rolling deploy from starting two instances near-simultaneously under `HEARTH_DB_MIGRATE=safe`.

Per plugin, in registry topological order:

1. **Partial-commit recovery check.** Compare the plugin's `alembic_version` head against `_hearth_schema_log` for that plugin. If the version table shows a revision applied but no audit row exists, the previous run failed between Alembic's commit and the audit write (or between the audit write attempt and its commit). For each such orphaned revision:
   - If the revision module defines `data_upgrade`: open a fresh `UnitOfWork` with `actor = PluginActor("<plugin>")`, call `await data_upgrade(uow)`, write the audit row in the same transaction, commit. The idempotency contract on `data_upgrade` makes the re-execution safe.
   - If the revision has no `data_upgrade`: just write the audit row (no work to re-do).
   - On failure of the recovery, abort the plan with a clear error pointing at the orphaned revision.
2. For each pending revision (Alembic's `walk_revisions`):
   - Import the revision module, read `HEARTH_UPGRADE_OPS`. Missing list = refuse with the clear error documented in "Revision file format".
   - For each `OpSummary` with `destructive=True`: `await confirm(revision, op_summary)`. If `False`, abort the plan (everything previously committed stays; this op and everything after is unapplied; return `AppliedReport` with abort point).
   - Call `alembic.command.upgrade(config, revision.revision_id)` — Alembic runs the revision's `upgrade()` against the DB inside its own transaction (transactional DDL on Postgres; batch-mode workaround on SQLite). On commit, the DDL is durable.
   - **If the revision module defines `data_upgrade`:** open a fresh `UnitOfWork` with `actor = PluginActor("<plugin>")`, call `await data_upgrade(uow)`, then write the audit row to `_hearth_schema_log` **in the same UoW**, commit. The audit row and the data live or die together — a failed commit leaves both undone, and the next run's recovery check (step 1) finds the orphan and re-executes.
   - **If the revision has no `data_upgrade`:** write the audit row to `_hearth_schema_log` immediately after Alembic's commit. If this write fails, the next run's recovery check will see the orphan (alembic_version advanced, no audit row) and write the audit row.
3. Move to next plugin.

**Atomicity is per-revision-DDL** (Alembic's default) plus per-revision-data (data UoW commits together with the audit row). The narrow window between Alembic's DDL commit and the start of the data UoW is the one place where a process crash can leave the DB in a recoverable-but-not-yet-recovered state — the recovery check handles this on the next run. Cross-revision rollback within a plugin requires the v2 rollback command. Per-plugin failure leaves earlier plugins applied, the failing plugin's last in-progress revision rolled back, and subsequent plugins unstarted — the operator gets a clear "stopped at plugin C, revision 0007 (data phase)" report.

### CLI surface

**Plugin developer commands** (run in plugin source tree during development):

```
hearth migrate generate <plugin>     Generate the next revision file from entity drift.
hearth migrate check <plugin>        CI dry-run: report drift but don't write.
```

**Operator commands** (run against a live DB):

```
hearth db init                       Create kernel tables (outbox, _hearth_schema_log).
hearth db status                     Per-plugin: applied head, declared head, drift summary.
hearth db plan                       Compute and print the full plan without applying.
hearth db migrate                    Apply the plan. Destructive ops trigger interactive prompts.
hearth db migrate --dry-run          Same as `plan` (alias for muscle-memory).
```

`hearth db migrate` is the only command that mutates. It prints the plan first, then for each destructive op:

```
DESTRUCTIVE: plugin=auth revision=0007
  description: Drop legacy email column
  op: DROP COLUMN user.email_legacy
Apply this op? [y/N]:
```

Default-N. `y` advances; `n` aborts the entire plan at that op (everything before stays committed). No "skip and continue" — partial application of a revision is exactly what Alembic's transactional `upgrade` prevents, and we honor that.

### Startup behavior

Set by env var `HEARTH_DB_MIGRATE`:

| Value | Behavior |
|---|---|
| `strict` *(default)* | If any migration is pending, refuse to start. Operator runs `hearth db migrate` explicitly. |
| `safe` | Auto-apply safe pending migrations on boot. If destructive ops are pending, refuse to start. |
| `off` | Skip the migration check entirely. For recovery, inspection, or known-out-of-sync staging environments. |

There is no `auto` that would apply destructive ops without a human in the loop. If you want destructive applied, you ran `hearth db migrate` first.

The kernel logs the startup decision loudly: "policy=safe; 3 safe migrations applied" or "policy=strict; refusing to start, 2 migrations pending (run `hearth db migrate`)".

**Plugin downgrade (package version goes backward).** If a plugin package downgrades — say `hearth-auth` goes from v1.5 back to v1.2 — the revision chain on disk is shorter than what Alembic's `alembic_version` row for the `auth` branch says is applied. The kernel detects this on boot under any policy other than `off` and refuses to start: "plugin `auth` has applied revisions through 0009 but only ships revisions through 0006; cannot proceed without rollback (not available v1)." Escape valve: restore-backup + redeploy-with-the-newer-package, or wait for v2 rollback.

### Rollback-aware design

V1 does not ship a rollback command. The design preserves the option without inventing anything custom:

1. **Every revision has `downgrade()`** — Alembic's standard. The autogenerator produces it; the author edits when needed (e.g., to reverse a backfill).
2. **The audit log records who acknowledged what destructive op, when** — answers "we want to roll back: was this destructive op's reversal previously authorized?"
3. **Per-plugin atomicity is Alembic's default** — when rollback ships, the unit is a revision, applied via Alembic's `downgrade` command. Per-plugin, in reverse topological order.
4. **No lossy recordkeeping** — every field in `_hearth_schema_log` is meaningful for audit today or for rollback tomorrow.

When rollback ships (v2 or later):

- `hearth db rollback <plugin>:<revision>` reverses everything applied for that plugin since (and including) the named revision, calling `alembic.command.downgrade(config, target)` per plugin.
- Cross-plugin rollback follows the inverse topological order.
- Destructive ops during rollback (yes, `downgrade` can be destructive too — dropping the column the upgrade added) follow the same confirmation flow.

## Out of scope v1 (and why)

- **Rollback execution.** Artifacts ready (Alembic's `downgrade()` is the standard); command not shipped. Rationale: one full release cycle of forward-only experience before we trust the reverse path in production. Escape valve: restore backup + redeploy older image.

- **Online / zero-downtime migrations.** Add-NOT-NULL-on-50M-row-table patterns; expand-contract column renames across deploys; long-running backfills in batches. These require app-level coordination across multiple deploys; the kernel does not pretend to solve them v1. Operators take brief downtime for destructive migrations. Documented as the "rebuild and redeploy" pattern.

- **Declarative destructive pre-authorization.** Rejected (2026-05-18). The right surface for "this destructive op is OK" is a human in front of a confirmation prompt, however that prompt is delivered (TTY, HTTP, etc.). A config-file pre-authorization (`HEARTH_ALLOW_DESTRUCTIVE=auth:0007`) is a bypass that hides the choice from the human who should be making it.

- **Marketplace install UX.** When a marketplace ships, "install plugin X" will use `Applier.apply(plan, confirm=...)` with a UX-appropriate `confirm`. The kernel API doesn't change.

- **Plugin re-adoption.** When an uninstalled plugin is reinstalled with its tables still present, v2 will add a `hearth db reattach <plugin>` command that reconciles. V1 logs a warning and refuses to apply (forcing operator action).

- **`@destructive` marker on `data_upgrade`.** V1 classifies all `data_upgrade` invocations as safe. An author who wants destructive data work surfaced to the operator routes it through `op.execute(...)` (the SQL classifier sees it). A future marker (e.g., `@destructive("deletes legacy permissions")`) would let Python data work be flagged too. Defer until the first real case asks for it.

## Open questions for the slice to force

These are deliberate stubs the spec does not pre-decide:

- **Should `hearth migrate generate` open the file in `$EDITOR` after writing?** Likely yes (Alembic does), but deferred.
- **`AlterColumnOp` lossy/lossless taxonomy.** V1 ships a conservative table; slice friction may justify finer granularity.
- **Index creation strategy on Postgres.** `CREATE INDEX CONCURRENTLY` is the standard zero-downtime pattern but cannot run inside a transaction — conflicts with per-revision atomicity. V1: regular `CREATE INDEX` inside the revision's transaction. Revisit if lock contention becomes a problem.
- **Audit log retention.** Never pruned? Pruned after rollback? Pruned by operator command? Defer.
- **Cross-plugin compound migrations.** Anything that requires plugin A's revision 5 to happen between plugin B's revisions 3 and 4. Not modeled. Plugins coordinate via events if needed. Slice will reveal whether this is acceptable.
